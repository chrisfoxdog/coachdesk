# CoachDesk v1 — Smoke Summary

Built 2026-11-08 from the Phase 0 specs (data model, privacy model, design system, layout system, concept brief) and the AutoCash AI pattern repo. Local only: no GitHub push, no Whop app registration, no Whop API calls, no deploy, no secrets in the repo.

## What was built

- **Data layer** (`server/db.ts`): all 14 entities from the data model (coaches, clients, membership_links, intake_forms, intake_responses, goals, session_logs, action_items, checkin_templates, checkins, needs_attention_flags, client_events, webhook_events, audit_log) as TypeScript types + a store interface with two implementations: Postgres (one JSONB table per entity, real `coach_id` column + tenant indexes, transactional) and a dev JSON file store (snapshot transactions). Production refuses to start without `DATABASE_URL`.
- **Webhooks** (`server/whop.ts`): `POST /api/webhooks/whop`, HMAC-SHA256 verification in Whop's standard-webhooks format (plus the legacy `t=,v1=` style Elite's other apps accept), 5-minute replay window, 401 on bad signature, dedupe on the Whop event ID before writes, minimized payload logging. Flows A/B/C implemented: activation creates the record + pending intake (or reactivates the *same* record), payment events only reflect Whop-reported status (+ past-due flag), deactivation archives only when the last live link ends — webhooks never delete.
- **Identity**: `x-whop-user-token` verified against Whop's JWKS via `jose`; coach scope = tenant from `WHOP_COMPANY_ID`; client scope = the single record whose `whop_user_id` equals the token's user ID. Production fails closed (401); dev-header fallback only when `NODE_ENV != production`; DB failure → `503 DATABASE_UNAVAILABLE`.
- **Coach UI**: roster (search, Active/Archived tabs, program week, status dots, open-flag badges), client record page (shared zone above coach-only zone per the design system; tags; goals CRUD + progress note + visibility toggle; 60-second session-log sheet with date chips and action-item rows, draft preserved on save failure; action items; intake answers; check-in history; timeline; per-client JSON export; confirmed record deletion), needs-attention inbox (severity bars, dismiss, resolved section), settings (intake form builder with field-JSON editor semantics + locked consent block using the privacy model's default template; check-in template editor; archived-retention months 3/6/12/24; goal-stale days; whole-book export; 24h support-access grant; danger-zone account deletion).
- **Client home**: separate component family fed only by `/api/me/*` endpoints — own shared goals, own action items (mark done), intake submit, weekly check-in submit, own answers, shared-only timeline, export-my-data, request-deletion. Session logs/wins/tags/flags are never queried by those endpoints.
- **Flags** (`server/flags.ts`): derived on read from dates/statuses/counts only — `intake_missing` (48h grace), `checkin_missed` (with consecutive-missed counting), `goal_stale` (default 14d, coach-set), `membership_past_due`; deduped per (client, type, period); weekly check-in instances auto-created and marked missed when past due.
- **Hard rules honored**: no AI anywhere (no AI key in `.env.example`, no AI calls — verified by repo scan); session notes hard-fixed `coach_only`; no prices/checkout/trial config anywhere (pricing is undecided — verified by scan); no seed/demo data at all (the dev store ships empty); honest copy throughout (no income or growth claims).
- **Theme choice (added 2026-11-08)**: dark/light toggle on top of the token system — no component was re-skinned. The `@theme` tokens in `src/index.css` remain the dark (brand) values; the light theme is one unlayered `[data-theme="light"]` override block redefining the same `--color-*` tokens (light blue-grey surfaces `#E9EEF5`/white/`#EEF2F7`, midnight text `#0F172A`, the *same* electric-blue accent — deliberately not redeclared). Semantic colors step deeper in light (emerald-700, amber-700, sky-600…) so their text forms keep AA contrast on light surfaces, and one new token, `--color-onbright`, carries badge/pill text on bright fills (`#020617` on the vivid dark fills, white on the deeper light fills — status styles and the two warning count pills in CoachApp now use it instead of `text-app`, so dark rendering is pixel-identical). `src/theme.ts` holds the logic: choice persists per browser in `localStorage` (`coachdesk-theme`), first load defaults to dark regardless of OS preference, and a tiny inline init script in `index.html` sets `data-theme` on `<html>` before first paint (no flash). The toggle (`ThemeToggle` in `src/components/ui.tsx`, ☀/☾ glyphs per the codebase's tab-bar convention) sits in the coach left rail, the mobile tab bar, Settings → Appearance, and the client-home header. No API, webhook, or data code touched; no new dependencies.

## Assumptions, stubs, and known simplifications

- **Tenant owner binding**: the tenant row is created on first webhook/visit with `whop_user_id` empty; the first verified non-client identity to open the app binds as the owner (that is the person who installed it). Recovery if ever mis-bound: clear `coaches.whop_user_id` in the database. Flagged here rather than hidden.
- **`@whop/sdk`** is declared (per the Elite stack) but v1 makes **no Whop API calls** — identity is JWKS, lifecycle is webhooks. Nothing in v1 needs the API.
- **Check-in cadence** is weekly (the MVP default in the specs); the `cadence` field exists on templates but other cadences are treated as weekly. Check-in periods are computed in UTC (Monday–Sunday); coach timezone is stored and used for display-level fields but period boundaries are UTC in v1.
- **`session_upcoming` flags** are not generated (they depend on Whop Calendar Bookings reads, which are not part of v1's webhook-only integration); the flag type exists in the model. The record header's "next session" line from the design system is likewise omitted rather than faked.
- **Session-log edit window** (7 days, design §6.4) is enforced by the API on PATCH; the "add a correction" path is simply logging a new entry — there is no correction-linking UI.
- **Form builder** edits field definitions through structured rows (label/type/required/options/help) rather than a raw JSON text editor — same data, safer editing.
- **Exports** are JSON (per-client, whole-book, client-own). The print/PDF view from the privacy model is not built in v1.
- **Retention auto-deletion** is not scheduled in v1: `archived_retention_months` is stored and shown, records archive and can be deleted manually, but no background job deletes on expiry yet.
- **Postgres path** is implemented and type-checked but not exercised against a live Postgres in this build (no database was provisioned — local-only scope). The full suite runs against the JSON store; the Postgres store shares the same interface and query shapes.
- The Whop **member name/email snapshot** comes from webhook payload fields (`user_name`/`name`/`username`, `email`) with graceful fallbacks; exact payload field names should be confirmed against a live sandbox event before launch (the standing Elite sandbox gate).
